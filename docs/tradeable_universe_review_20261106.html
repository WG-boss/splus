原策划案（下称 B1）的评审标准是"国际机构级"。但本项目的真实运行环境是：单一决策者、单一账户、6 条定时任务全年无人值守、可用历史为指数日线（ETF 溢价/成交额历史短）、已有一套经过 14 项自检验证的 L1–L5。机构级 ≠ 项目级最优。构造五个候选：

方案定义一句话

B1 原案完整版资格分引擎 + 三簿册 pod 硬隔离 + 完整生命周期状态机 + 矩阵校准（19 参数）机构级全套

三、逐项论证：为什么 B1 的三个重机制在本项目站不住

3.1 三簿册 pod 硬隔离 → bucket_max 系数表（本次复审最大发现）

pod 隔离（Citadel 式）解决的问题是"多策略团队互不干扰"。本项目只有一个策略、一个账户、一个决策者——硬隔离没有服务对象。而复审中发现：现有 L3 代码已实现按桶上限机制（engine.py:1132，cap = clamp(vol_target/vmax, 0, bucket_max)），core/theme/ai_hw/pharma/watch 各桶上限已是配置项。

B1：三簿册 pod 硬隔离B2：bucket_max 系数表扩展
新概念3 个簿册 + 预算隔离层 + 跨簿册相关性口径改造零新概念——一张系数表（如 core 1.0 / theme 0.7 / ai_hw 0.6 / pharma 0.7 / watch 0）
L3 代码改动预算层重写 + 相关性惩罚跨簿册口径零行——机制已存在，只改配置
风险预算表达硬隔离 50/35/15系数表连续调节，同样能表达 50/35/15（系数∝预算），且可微调
回滚需下线簿册层改回旧系数表即回滚

3.2 "簿册"概念 → 现有 role 字段归并（第二发现）

B1 需要把 12 只标的"归位"进三个簿册，并为 106 只 watch 定义候选簿册归属——这引入了一套新的分类体系。但 config.yaml 里 role 字段已存在且语义完备（进攻候选/左侧候选/事件驱动/上游映射/固定跟踪/领先观察 + 参照类）。把 role 归并为三个"角色族"：

角色族（新增，仅 1 个映射表）吸纳的现有 role投研语义
进攻族进攻候选、上游映射、固定跟踪B/C 态主战场，行业贝塔+
事件族事件驱动、左侧候选A 态左侧专用通道（原 Tactical 的灵魂）
参照族市场基准、风格参照、全球上游、领先观察、筛选源观察不占预算，资格分仅作温度计

StateFit 矩阵变为 5 态 × 3 角色族 = 15 格（与 B1 参数量持平），但概念从"新建簿册体系"降为"给现有字段加一张查表"。11-05 实测：进攻族 7 只（6 只 E 态 → StateFit=0，光模块/PCB 等全冻结）、事件族 3 只、恒生科技为领先观察属参照族但跨境独立（需一条特例：参照族中 confirmed 且境外市场者按 0.5 计入）。

3.3 完整生命周期状态机 → 两条连续性规则 + 冷却（第三发现）

B1 的五态生命周期（Watch→Candidate→Confirmed→Active⇄Probation→Exit）本质是把机构组合治理流程制度化。单人体系中，状态机的价值只剩防抖动——而这用两条规则即可达到 90% 效果：

B1 状态机B2 轻量替代损失
五状态 + JSONL 落盘 + 事件台账全链规则 1（晋升）：资格 ≥80 连续 3 日 + 映射 confirmed → tradeable 投影置 true；规则 2（降级）：tradeable 标的资格连续 5 日 <60 或 E 态超期（进攻族 5 日/事件族 3 日）→ 置 false；冷却：降级后 10 交易日禁止再晋升丢失"Probation 中间态"的渐进退出——但 L4 失效位与 L5 kill switch 已覆盖离场执行，中间态在单人体系里是冗余流程
事件写独立台账事件写入现有归因台账（新增 lifecycle 桶）无损失——归因闭环保留
本质区别：B1 的生命周期是"重新发明一套机构流程"，B2 是"用两条规则守门 + 复用现有台账"。B1 的渐进退出价值已被现有 L4/L5 覆盖——这是复审中确认的最重要的"已有资产替代"。

3.4 B3（白名单扩充）为什么不够

B3 能解决"E 态占位"（扩名单后新鲜血液进得来），但解决不了"动态退出"与"全量定价"：① 40 只名单在下次状态切换时同样会老化——B3 是把 T+N 周改成 T+N 月，没有消除人工时滞；② 没有 StateFit 权重，40 只在 L3 里平等竞争，行业同质化时相关性惩罚会把全组合仓位压扁（光模块/PCB/半导体材料同涨同跌的老问题）；③ 但 B3 的"一次性批量确认 30–40 只映射"动作本身有价值——它恰好是 B2 的 P4 前置工作。结论：B3 被吸收为 B2 的一个子步骤，而非独立方案。

3.5 B4（LLM 增强）为什么出局

项目铁律"零外部脆弱点、仅 4 个 LLM 兜底点"。每日标的解读引入：API 可用性依赖（cron 半夜失败即断链）、输出不可回放（违背资格分可回放原则）、成本随 universe 规模线性增长。降级保留：P4 阶段可用 LLM 辅助生成"晋升标的 premetem 草稿"，但仅作为人工确认的输入，不进入决策链。

六、复审结论

裁定内容
保留资格分引擎（四因子）、四档权限、StateFit 匹配思想、资格分落盘回放、执行工程全套、fail-closed、回滚设计——B1 的全部灵魂
降级三簿册 → bucket_max 系数表；"簿册"概念 → role 角色族查表；五态状态机 → 2 条规则 + 冷却 + 现有台账
出局pod 硬隔离与跨簿册相关性改造（无服务对象）；LLM 进决策链（违背零脆弱点）；独立生命周期台账（已有归因台账替代）
吸收B3 白名单扩充 → 成为 P4 的批量确认动作；B4 LLM → 降为 P4 辅助草稿工具

一句话总纲：B1 回答"机构会怎么做"，B2 回答"这套代码、这个人、这个 cron 环境，怎么把机构智慧落进现有架构"——后者才是 SSSSS 级的真正含义：不是堆机制，是每个机制都长在它该长的地方。
